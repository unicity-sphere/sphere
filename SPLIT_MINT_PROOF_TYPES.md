# Understanding Two Types of Proofs in Token Splits

## Overview

There are TWO completely different types of Merkle proofs involved in token splits:

### 1. Inclusion Proofs (from Aggregator)
### 2. Split Reason Proofs (embedded in mint transaction)

These are NOT the same, and only Type 1 should ever be regenerated.

## Proof Type Comparison

```
┌─────────────────────────────────────────────────────────────────────────┐
│                         TOKEN SPLIT FLOW                                 │
└─────────────────────────────────────────────────────────────────────────┘

Step 1: BURN TRANSACTION
┌──────────────────────────────────────────────────────────────────────┐
│  Original Token (1000 coins)                                         │
│  ↓                                                                    │
│  Transfer to BurnPredicate                                           │
│  ↓                                                                    │
│  Submit to Aggregator                                                │
│  ↓                                                                    │
│  ┌────────────────────────────────────────────────────────┐          │
│  │ TYPE 1: INCLUSION PROOF (from aggregator)              │          │
│  │                                                         │          │
│  │ - Proves burn transaction was included in tree         │          │
│  │ - Contains Merkle path from leaf to root               │          │
│  │ - Changes as tree grows (path gets longer)             │          │
│  │ - CAN be regenerated by querying aggregator            │          │
│  │ - Stored in Token.stateProof                           │          │
│  │                                                         │          │
│  │ Structure:                                              │          │
│  │   {                                                     │          │
│  │     requestId: "abc123",                                │          │
│  │     root: "0x...",                                      │          │
│  │     steps: [                                            │          │
│  │       { path: "0", data: "0x..." },  // sibling hash   │          │
│  │       { path: "1", data: "0x..." },  // sibling hash   │          │
│  │       ...                                               │          │
│  │     ]                                                   │          │
│  │   }                                                     │          │
│  └────────────────────────────────────────────────────────┘          │
└──────────────────────────────────────────────────────────────────────┘

Step 2: MINT TRANSACTIONS (2 new tokens)
┌──────────────────────────────────────────────────────────────────────┐
│  Token A (600 coins)                                                 │
│  Token B (400 coins)                                                 │
│  ↓                                                                    │
│  ┌────────────────────────────────────────────────────────┐          │
│  │ TYPE 2: SPLIT REASON PROOFS (in mint transaction)      │          │
│  │                                                         │          │
│  │ - Proves the burn had the claimed coin structure       │          │
│  │ - Part of the mint transaction data itself             │          │
│  │ - IMMUTABLE (changing it changes transaction hash)     │          │
│  │ - CANNOT be regenerated (would invalidate mint)        │          │
│  │ - NOT an aggregator inclusion proof                    │          │
│  │ - Stored in MintTransactionData.reason                 │          │
│  │                                                         │          │
│  │ Structure:                                              │          │
│  │   {                                                     │          │
│  │     type: "TOKEN_SPLIT",                                │          │
│  │     token: { ...burned token... },                      │          │
│  │     proofs: [                                           │          │
│  │       {                                                 │          │
│  │         coinId: "0x...",                                │          │
│  │         aggregationPath: {  // ← LOCAL TREE PATH        │          │
│  │           root: "0x...",                                │          │
│  │           steps: [...]                                  │          │
│  │         },                                              │          │
│  │         coinTreePath: {     // ← LOCAL TREE PATH        │          │
│  │           root: "0x...",                                │          │
│  │           steps: [...]                                  │          │
│  │         }                                               │          │
│  │       }                                                 │          │
│  │     ]                                                   │          │
│  │   }                                                     │          │
│  └────────────────────────────────────────────────────────┘          │
│  ↓                                                                    │
│  Submit to Aggregator                                                │
│  ↓                                                                    │
│  ┌────────────────────────────────────────────────────────┐          │
│  │ TYPE 1: INCLUSION PROOF (for mint transaction)         │          │
│  │                                                         │          │
│  │ - Proves mint transaction was included in tree         │          │
│  │ - CAN be regenerated                                   │          │
│  └────────────────────────────────────────────────────────┘          │
└──────────────────────────────────────────────────────────────────────┘
```

## Key Differences

| Aspect | Type 1: Inclusion Proof | Type 2: Split Reason Proof |
|--------|------------------------|----------------------------|
| **Purpose** | Prove transaction was included in aggregator tree | Prove burn had correct coin structure |
| **Source** | Aggregator service | TokenSplitBuilder during split creation |
| **Location** | `Token.stateProof` | `MintTransactionData.reason.proofs` |
| **Mutability** | Can be regenerated | IMMUTABLE (part of tx hash) |
| **Tree** | Global aggregator tree | Local split tree (coin distribution) |
| **Changes** | Path grows as tree grows | Never changes |
| **API** | `getInclusionProof(requestId)` | Created during `TokenSplitBuilder.build()` |

## What Each Proof Verifies

### Type 1: Inclusion Proof
```typescript
// Verifies: "This transaction (with this hash) exists in the aggregator tree"
// 
// Verification process:
// 1. Start with transaction hash (leaf)
// 2. Follow path steps (left/right, sibling hashes)
// 3. Compute intermediate hashes up the tree
// 4. Compare final hash with published root
//
// Example:
const proof = await aggregatorClient.getInclusionProof(requestId);
const isValid = await proof.verify();
// Returns true if transaction is in the tree
```

### Type 2: Split Reason Proof
```typescript
// Verifies: "This mint was created from a valid token burn"
//
// Verification process:
// 1. Check that source token is burned (has BurnPredicate)
// 2. Verify each coin's aggregation path
//    - Proves coin existed in the burned token
//    - Verifies path leads to burn reason hash
// 3. Verify each coin's tree path
//    - Proves new token gets correct coin amount
//    - Verifies distribution is correct
// 4. Check that total coins match (no creation/destruction)
//
// Example:
const reason = mintTransaction.data.reason; // SplitMintReason
const result = await reason.verify(mintTransaction);
// Returns OK if split was done correctly
```

## Critical Insight: Local Trees vs Global Tree

### Global Aggregator Tree
```
                      Root (published to blockchain)
                     /                              \
                    /                                \
              Branch 1                            Branch 2
              /      \                            /      \
         Tx1 ... Burn Transaction          Mint A ... Mint B
         
         ← TYPE 1 proofs go here (aggregator inclusion)
```

### Local Split Trees (created during burn)
```
When you burn a token with multiple coins, TokenSplitBuilder creates:

1. Aggregation Tree (coins in burn)
   
              Aggregation Root → stored in BurnPredicate.reason
             /                  \
        Coin1                  Coin2
        (600)                  (400)
        
2. Coin Tree (distribution to new tokens)

        For Coin1:
              Coin Tree Root
             /              \
         Token A          Token B
         (600 coins)      (0 coins)
         
        For Coin2:
              Coin Tree Root
             /              \
         Token A          Token B
         (0 coins)        (400 coins)

← TYPE 2 proofs come from these trees (split structure)
```

## During Token Recovery

### What Happens
```typescript
// 1. Load token from IPFS
const token = await loadFromIPFS(cid);

// 2. Check if token needs proof regeneration
if (!token.stateProof || isProofStale(token.stateProof)) {
  // 3. Regenerate TYPE 1 proof (inclusion proof)
  const newProof = await aggregatorClient.getInclusionProof(token.requestId);
  token.stateProof = newProof;  // ✅ SAFE - external to transaction
}

// 4. TYPE 2 proofs (split reason) are NEVER regenerated
// They're part of the transaction data itself:
const mintReason = token.mintTransaction?.data?.reason;
// This contains the original split proofs from creation time
// Changing them would change the transaction hash → INVALID TOKEN
```

### Why This Works
1. Type 1 proofs are EXTERNAL to the transaction data
   - They prove the transaction exists in the tree
   - Regenerating them doesn't change the transaction
   - They're stored separately in `Token.stateProof`

2. Type 2 proofs are INTERNAL to the transaction data
   - They're part of `MintTransactionData.reason`
   - They were created at split time
   - They prove the split was valid at that moment
   - They never need to be updated because the burn is permanent

## Analogy

Think of it like a birth certificate:

- **Type 1 Proof (Inclusion)**: The government's database record that confirms your birth certificate exists
  - Can be reprinted/regenerated
  - Just proves "yes, this certificate is real"
  
- **Type 2 Proof (Split Reason)**: The actual details on your birth certificate (parents, date, location)
  - CANNOT be changed
  - Part of the document itself
  - Changing them would make it a different certificate

## Conclusion

When you see Merkle paths in Unicity tokens, ask:

1. **Is this an inclusion proof from the aggregator?**
   - YES → Can be regenerated safely
   - Located in `Token.stateProof`

2. **Is this a split reason proof in the mint transaction?**
   - NO → CANNOT be regenerated
   - Located in `MintTransactionData.reason.proofs`
   - Part of the transaction hash

The system is designed so that:
- External proofs (Type 1) can be updated as the tree grows
- Internal proofs (Type 2) are immutable and never need updating
